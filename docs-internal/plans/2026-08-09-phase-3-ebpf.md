# Phase 3: eBPF CUDA-Tracing Exporter — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or
> superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax.

> **Commit policy — read before starting.** `CLAUDE.md` states *"Do not automatically commit until I approve."*
> Every "Commit" step below means: **stage the files, show the diff, and ask for approval.** Do not run
> `git commit` unattended. Commit messages must be brief and carry no AI co-author trailer.

**Goal:** Deploy per-pod CUDA API tracing — launch rate and latency, allocation and transfer volume,
synchronization waits, CUDA errors, and HAMi's throttle and OOM behaviour measured directly — under the
`ebpf_cuda_*` / `ebpf_hami_*` names.

**Architecture:** Both upstream repositories become git submodules of this one, so the build is reproducible
from this repository alone. The only source change is a rename of twenty Prometheus metric names in the core.
The legacy agent already running on the cluster is snapshotted and removed, not supplemented.

**Tech Stack:** Go (upstream build), eBPF/uprobes, git submodules, Docker → GHCR, plain numbered YAML.

**Prerequisites:**
- [Phase 2](2026-08-09-phase-2-nvml.md) complete — Prometheus scraping, `scripts/promq.sh` working,
  gpu-burn image available, and the backend's real memory consumption measured.
- **Storage upgraded.** Phase 0 left Prometheus on `emptyDir`. This exporter is the first thing that makes
  long-window aggregates worth keeping, and it multiplies the series count by roughly an order of magnitude.
  Replace `emptyDir` with a local PersistentVolume before Task 6 ([07 § 3.3](../07-backend-and-deployment.md)).

**Why this phase is last:** the eBPF exporter produces roughly ten times the series of every other source
combined. Sizing done before it is running is meaningless, which is why the cheap exporters land first.

```markdown
## Making a change

A change is a three-step promotion, and skipping a hop loses it:

1. Edit the core (`.obi-src`), commit there.
2. Bump the agent's `.obi-src` pointer, commit there.
3. Bump this repository's `eBPF-Lens` pointer, commit here.

A change made only in the agent's vendored copy is lost at the next sync; a
change made only in the core never reaches a built image.

## Build

    git submodule update --init --recursive
    cd eBPF-Lens && make docker-build   # see the upstream Makefile for targets

CI checks out with `--recurse-submodules`; the image's provenance is the
submodule pointer pair.
```

### Task 2: Rename the metrics in the core

Upstream emits the GPU families under a `gpu_*` prefix. We rename to `ebpf_cuda_*` / `ebpf_hami_*` (D-12), so
prefix-by-source becomes universal and the eBPF HAMi families stop sitting confusingly next to vGPUmonitor's
`hami_*`, which measure something entirely different.

**This is a one-way door.** Renaming after dashboards exist means rewriting every panel and recorded rule.

**Files:**
- Modify: `exporters/ebpf/eBPF-Lens/.obi-src/pkg/export/attributes/metric.go`
- Modify: `exporters/ebpf/eBPF-Lens/.obi-src/pkg/export/prom/prom_test.go`

- [ ] **Step 1: Write the failing test**

```bash
cd exporters/ebpf/eBPF-Lens/.obi-src
grep -c 'Prom: *"gpu_' pkg/export/attributes/metric.go   # must become 0
grep -c 'Prom: *"ebpf_' pkg/export/attributes/metric.go  # must become 20
```

- [ ] **Step 2: Run the test to verify it fails**

Expected: `20` then `0` — the opposite of the target.

- [ ] **Step 3: Rename the `Prom` field only**

Metric identities are a three-field record:

```go
type Name struct {
    Section Section  // attribute-selection configuration key
    Prom    string   // Prometheus exporter name    <- only this changes
    OTEL    string   // OpenTelemetry exporter name
}
```

Changing only `Prom` leaves existing `attributes.select` configuration keys working and OTLP semantic
conventions untouched.

```bash
cd exporters/ebpf/eBPF-Lens/.obi-src
sed -i 's/\(Prom: *"\)gpu_cuda_/\1ebpf_cuda_/; s/\(Prom: *"\)gpu_hami_/\1ebpf_hami_/' \
  pkg/export/attributes/metric.go
sed -i 's/"gpu_cuda_/"ebpf_cuda_/g; s/"gpu_hami_/"ebpf_hami_/g' \
  pkg/export/prom/prom_test.go
```

- [ ] **Step 4: Run the test to verify it passes**

```bash
cd exporters/ebpf/eBPF-Lens/.obi-src
grep -c 'Prom: *"gpu_' pkg/export/attributes/metric.go   || true   # expect 0
grep -c 'Prom: *"ebpf_' pkg/export/attributes/metric.go            # expect 20
grep -c 'Section: *"gpu\.' pkg/export/attributes/metric.go         # unchanged
grep -c 'OTEL: *"gpu\.' pkg/export/attributes/metric.go            # unchanged
```

Expected: `0`, `20`, and the `Section`/`OTEL` counts unchanged from before the edit.

- [ ] **Step 5: Run the upstream unit tests**

```bash
cd exporters/ebpf/eBPF-Lens/.obi-src
go test ./pkg/export/... 2>&1 | tail -20
```

Expected: `./pkg/export/attributes/...` PASSES.

**`./pkg/export/prom/...` will NOT build on a fresh checkout, and that is not caused by the rename.** The
eBPF bindings (`StatsObjects`, `NetFlowId`, `LoadStats`) are generated by `bpf2go` and are absent until the
Makefile's generate step has run; the failures are byte-identical with the rename stashed. Confirm that before
blaming the edit, then test the package actually changed:

```bash
go test ./pkg/export/attributes/...
```

The Docker build runs generation itself, so this does not block Task 4. A failure naming the old metric string
is a real failure — fix it in the test, not by reverting the rename.

- [ ] **Step 6: Commit in the core, then promote**

```bash

git checkout -b rename-gpu-metrics-to-ebpf
git add pkg/export/attributes/metric.go pkg/export/prom/prom_test.go
git diff --cached --stat
# suggested message: "rename gpu_* prometheus metrics to ebpf_*"
```

Then bump the agent's pointer and this repository's pointer, as the README describes. Request approval for

```yaml
metadata:
  name: ebpf-gpu-exporter
```

- [ ] **Step 7: Measure cardinality against the Phase 0 assumption (A-5)**

```bash
  || kubectl -n "$NS" get pod -l app.kubernetes.io/name=prometheus
```

Expected: the eBPF count dominates by roughly an order of magnitude. **Record both numbers and Prometheus's
actual memory use**, then revise the Prometheus resource requests if they are exceeded.

If cardinality is far above the estimate, reduce **label dimensions** — aggregating over CUDA function name,
for example — rather than removing metric families. A dropped dimension loses detail; a dropped family loses a
capability ([05 § 5](../05-exporter-ebpf.md)).

- [ ] **Step 8: Check for series churn on a bursty workload**

The agent expires a series whose flow has been idle beyond a TTL, which breaks `rate()` over long windows and
makes counters look like they reset.

```bash
./scripts/promq.sh 'count(count by (__name__) ({__name__=~"ebpf_cuda_.*"}))'
```

Expected: the count falls as series expire — that is the designed behaviour, not a fault. Confirm the scrape
interval is well below the agent's expiry so continuous workloads never gap.

      (Task 7 Step 3)

      (Task 7 Step 4)
- [ ] **No `gpu_cuda_*` or `gpu_hami_*` series exists anywhere** — the rename is complete and no old agent
      survives (Task 7 Step 6)
- [ ] The legacy agent is removed and its configuration snapshot stored outside this repository (Task 5)
- [ ] No host-port collision between the three exporters (Task 5 Step 8)

      exceeded (Task 7 Step 7) — **A-5**
