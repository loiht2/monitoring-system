# Phase 4: MIG Validation — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or
> superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax.

> **Commit policy — read before starting.** `CLAUDE.md` states *"Do not automatically commit until I approve."*
> Every "Commit" step below means: **stage the files, show the diff, and ask for approval.** Do not run
> `git commit` unattended. Commit messages must be brief and carry no AI co-author trailer.

**Goal:** Prove the whole stack works when a GPU is partitioned — DCGM reporting per-instance, allocation
carrying the instance identity, NVML degrading in the documented way, and the dashboards resolving to the
right source per device mode. Settle assumptions **A-8** and **A-9**.

**Architecture:** No new components. MIG is enabled on **exactly one device**; every other device in the fleet
stays whole, so this validates a *mixed* fleet — which is both the realistic case and the only way to keep
existing GPU work running while the validation proceeds.

**Tech Stack:** NVIDIA GPU Operator MIG manager (`nvidia-mig-parted` config), DCGM, the exporters from Phases
1-3, Grafana.

**Prerequisites:** [Phase 3](2026-08-09-phase-3-ebpf.md) complete — all three exporters deployed and
validated on whole GPUs.

**Why MIG is worth its cost:** a MIG instance is exclusively assigned, so entitlement *is* attribution and
every hardware metric on that instance belongs to exactly one pod. It is the one case where partitioning makes
observability better rather than worse ([09 § 4](../09-risks-and-open-questions.md)).

## Environment variables used throughout

```bash
export NS=gpu-monitoring
export DCGM_NS=<namespace where the DCGM exporter runs>
export CLUSTERPOLICY=<name>        # kubectl get clusterpolicies.nvidia.com -o name
export NODE=<the GPU node>
export MIG_DEVICE=1                # index of the ONE device to partition
export KEEP_DEVICE=0               # index that must stay whole
```

`MIG_DEVICE` must **not** be a device that existing workloads are pinned to. Check first — device selectors in
other projects' manifests are the usual place this is written down.

---

## Before you start: this is a disruptive, reversible change

| | |
|---|---|
| **Enabling MIG needs the device idle.** | Any process holding it blocks the mode change |
| **It rewrites the device topology.** | Whole-device allocation entries for that device disappear and are replaced by instances |
| **Node labels can lie about MIG state.** | A device manager can report a configuration it never applied. `nvidia-smi` is the only truth ([08 § 5](../08-validation.md)) |
| **It is reversible.** | Task 8 restores the device to whole. Read that task before starting Task 2 |


- [ ] **Step 2: Run the test to verify it fails**

Expected: FAIL — `NOT as intended`, because both devices are currently whole.

- [ ] **Step 3: Write a per-device MIG configuration**

The MIG manager's config format selects devices by index, which is what makes a mixed fleet possible. Replace
`<profile>` and the count with values from the profile list recorded in Task 1 Step 4.

`deploy/a30-node/31-mig-config.yaml`:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: gpu-mig-config
  namespace: gpu-operator      # the GPU Operator's namespace
data:
  config.yaml: |
    version: v1
    mig-configs:
      # Exactly one device is partitioned. Every other device stays whole so
      # existing GPU work keeps running and the mixed-fleet case is exercised.
      one-device-mig:
        - devices: [0]
          mig-enabled: false
        - devices: [1]
          mig-enabled: true
          mig-devices:
            "<profile>": <count>
      # Restores the fleet. Referenced by the rollback in Task 8.
      all-disabled:
        - devices: all
          mig-enabled: false
```

- [ ] **Step 4: Enable the MIG manager and point it at the config**

The GPU Operator ships the MIG manager disabled by default. Enable it and select our configuration:

```bash
kubectl apply -f deploy/a30-node/31-mig-config.yaml
kubectl patch clusterpolicies.nvidia.com "$CLUSTERPOLICY" --type merge -p '{
  "spec": {"migManager": {"enabled": true, "config": {"name": "gpu-mig-config", "default": "all-disabled"}}}
}'
kubectl -n gpu-operator rollout status ds/nvidia-mig-manager --timeout=300s
kubectl label node "$NODE" nvidia.com/mig.config=one-device-mig --overwrite
```

Then wait for it to converge and **read the result from the hardware**:

```bash
for _ in $(seq 1 30); do
  kubectl get node "$NODE" -o jsonpath='{.metadata.labels.nvidia\.com/mig\.config\.state}{"\n"}'
  sleep 10
done
nvidia-smi --query-gpu=index,mig.mode.current --format=csv
nvidia-smi -L
```

Expected: the label reaches `success` **and** `nvidia-smi` shows the intended device Enabled with instances
listed. If the label says `success` while `nvidia-smi` disagrees, the label is lying — believe `nvidia-smi`
and investigate the MIG manager's logs before continuing.

If the MIG manager cannot be enabled on this cluster, the fallback is direct configuration
(`nvidia-smi -i "$MIG_DEVICE" -mig 1` then `nvidia-smi mig -i "$MIG_DEVICE" -cgi <profile> -C`), which does
**not** survive a node reboot. Record which route was taken — Task 8's rollback differs.

### Task 5: NVML degrades in the documented way

Under MIG the driver does not sample per-process utilization. Per-process **memory** survives, but only on the
instance handle — which is why the exporter enumerates instance handles separately.

- [ ] **Step 1: Write the failing test**

```bash
# On the partitioned device: memory yes, utilization no.
./scripts/promq.sh 'count(nvml_process_gpu_memory_bytes)'
./scripts/promq.sh 'count(nvml_process_sm_utilization_ratio)'
```

- [ ] **Step 2: Run the test to verify it fails**

Before a MIG workload runs, the first is `(empty result)`.

- [ ] **Step 3: With the MIG workload running, verify the split**

```bash
./scripts/promq.sh 'nvml_process_gpu_memory_bytes'
./scripts/promq.sh 'nvml_process_sm_utilization_ratio'
```

Expected: the MIG pod appears in the **memory** query and **not** in the utilization query. A pod on the whole

- [ ] **Step 4: Verify utilization is absent, not zero**


Expected: `(empty result)`. A zero here would be indistinguishable from a real measurement and would corrupt
every average computed over it ([02 § 5.2](../02-metric-catalog.md)).

### Task 6: A-8 — is per-instance utilization normalized to the instance?

**The measurement that decides how every MIG utilization panel must be written.** Published sources disagree:
one reports instances never reaching 1.0 under saturation, another that a saturated small instance reads 100%
locally. It must be measured, not assumed.

- [ ] **Step 1: Write the failing test**

```bash
test -s baselines/mig-normalization.txt && echo "answered" || { echo "UNANSWERED"; false; }
```

- [ ] **Step 2: Run the test to verify it fails**

Expected: FAIL — `UNANSWERED`

- [ ] **Step 3: Saturate the smallest instance and read the value**

Run the load generator on **one** instance, sized so the workload cannot be the limiting factor, and let it
reach steady state:

```bash
sleep 90
./scripts/promq.sh 'DCGM_FI_PROF_GR_ENGINE_ACTIVE{GPU_I_ID!=""}'
./scripts/promq.sh 'DCGM_FI_PROF_SM_ACTIVE{GPU_I_ID!=""}'
nvidia-smi mig -i "$MIG_DEVICE" -lgip
```

- [ ] **Step 4: Record the answer**

```bash
{
  echo "profile under test: <name>, SM count: <n>, device SM total: <n>"
  echo "GR_ENGINE_ACTIVE at saturation:"
  ./scripts/promq.sh 'DCGM_FI_PROF_GR_ENGINE_ACTIVE{GPU_I_ID!=""}'
} > baselines/mig-normalization.txt
cat baselines/mig-normalization.txt
```

Interpretation:

| Reading | Meaning | Consequence for queries |
|---|---|---|
| ≈ **1.0** | **Instance-normalized** | Use the value directly. "80% busy" means 80% of the instance |
| ≈ instance SMs ÷ device SMs | **Device-normalized** | Multiply by `device SMs ÷ instance SMs` to get instance-local utilization — which is exactly what MIG catalog row 2 exists to supply |
| Anything else | Neither | Do not build a utilization panel on it. Record the observation and escalate |

- [ ] **Step 5: Run the test to verify it passes**

Run the Step 1 command.
Expected: PASS — `answered`

- [ ] **Step 6: Record the result against A-8**

Update [09 § 2](../09-risks-and-open-questions.md) with the measured answer, replacing the assumption with a
fact. **This is the most valuable output of the phase** — it is the one thing no amount of reading settles.
